# Architecture reuse decisions — P3

Date: 2026-11-22  
Reference: Golden Agentic Engineering v0.1.0-dev at `dc2ece864b2d744e47dfe8c7d9ad78aadbed369e`. Golden is a pre-qualification development-method foundation; its standards are not represented as enforced or company-approved.

## Product UI and single workspace

**Selected:** One P3 UI foundation: React 19 / TypeScript, Vite, and the locally locked Apache ECharts runtime. P3 includes a small loopback reference host so engineers can run the MCP-to-C01–C05-to-evidence workflow without another product or suite. It performs bounded workflow requests, displays P3 capability and provenance details, renders typed observations, supports cancel/refusal/recovery, and exports canonical evidence. This host is a P3 product runtime, not a generalized suite shell. The separately exported `P3Panel` and `suite-ui-module.v1` manifest provide the future shared-host contribution. The same Vite/Vitest lock runs both the standalone host and panel suites; `npm test` currently passes all 15 tests.

**NiceGUI Base audit:** An installed `nicegui-base==3.0.0a8` package was found and inspected at source commit `000298562d6bcbf6df304edbd41b98b30fe4bfcf` (the package reports 1,022 installed files totaling 13,074,408 bytes, including bytecode caches, and 334 Python source files). Its upstream README calls this version a source-complete alpha and says live target, browser, and human certification remain pending. It contains useful wafer radial/sector/center-edge and ECharts surfaces, but its Python/NiceGUI runtime does not compose with the selected React module. Its installed distribution has no license metadata or embedded root license, so P3 cannot redistribute it on the available evidence. See the [NiceGUI Base repository](https://github.com/kimhw8084/nicegui-base) and its pinned [source commit](https://github.com/kimhw8084/nicegui-base/tree/000298562d6bcbf6df304edbd41b98b30fe4bfcf). P3 instead uses one P3-owned React foundation for the standalone workflow and embeds the same `P3Panel` contract for future suite integration. The 15 host/module tests and real synthetic browser workflow pass; formal engineer study and P1's actual route remain separate gates.

**React/tooling audit:** The P3 lock pins React 19.2.0, React DOM 19.2.0, Vite 7.3.8, TypeScript 5.9.3, Vitest 5.1.1, Testing Library, happy-dom, and ECharts 6.1.0. Tailwind and shadcn are not staged; semantic HTML and the existing component conventions suffice. The P3 package tests both its headless shared-host panel and the independent reference host. Strict TypeScript, all 15 Vitest cases, production assets, and the real local browser workflow have been verified against current P3 source. This does not clear P1 route integration or a formal engineer accessibility study.

**Integration status:** The live local P1 snapshot exposes `C01`–`C05`, `suite-spatial-map.v1`, the shared ECharts renderer, `SuiteHost`, and `/fab-intelligence/p3`; P3's manifest matches its registered contribution. P3's panel was mounted using P1's actual shared renderer, with strict type checking, exact observation counts, and no interpolation. The current P1 Python suite passes 154 tests with 16 optional SDK skips; its UI suite passes 39 tests, typecheck and production build pass. The P1 acceptance run still fails typed categorical conversion: numeric category and defect codes are stringified, unlabeled defect events count as missing, and numeric strings pass as categorical strings in continuous maps. P1 also routes a stale P3 engine/panel copy. The exact P1-owned v2 contract correction and failing regression cases are in `proposals/CHANGE-002-p3-spatial-map-and-capability-extension.md` and `release/P1_MODULE_INTEGRATION_EVIDENCE.json`. No shared contract was modified in P3.

## Visualization and tables

**Selected:** Apache ECharts 6.1.0 for the interactive measured-site view and semantic HTML tables as the accessible data path. The P3 host bundles its pinned assets for offline use. P1's local bake-off measured ECharts at 218.27 KB gzip and Plotly.js core + scatter at 454.46 KB gzip; the comparison reported about 52% less gzip JavaScript for ECharts. P3's suite module also accepts the shared host renderer callback and does not create a second chart abstraction. The selection reuses one visualization library and does not claim an integrated P1 renderer pass. Timings are a single local observation, not a repeated benchmark.

| Candidate | P3 decision | Local evidence and cost |
|---|---|---|
| Apache ECharts | Use for P3 standalone and shared-foundation adapter | P3 pins and bundles ECharts 6.1.0 for the measured-site map. Its suite module also accepts the host renderer callback, so the suite can keep one visualization library without making P3 depend on P1. |
| Plotly.js 4.3.0 | Do not add | In P1's matched build it was 454.46 KB gzip JS + 10.59 KB CSS versus ECharts at 218.27 KB gzip JS; no P3 gain offsets a second renderer. |
| AG Grid Community 36.3.0 | Do not add | P1's accessible table path is native HTML. The reviewed unpacked package was 21,947,043 bytes; no P3 workflow or measured task requires a separate grid. |
| Cytoscape.js 3.35.0 | Not applicable | The reviewed package was 5,814,108 unpacked bytes. P3 has no graph model/workflow; a graph would also risk implying unapproved manufacturing relationships. |

P1's candidate bake-off reused locked local packages and reported no known advisories in the available audit data; it is not company license clearance or host qualification. These are reuse and scope decisions, not claims of a P3 map-rendering benchmark. P3 qualifies its own map and typed table; a future suite host separately qualifies shared rendering.

## Backend, tests, and offline packaging

P3 exposes its deterministic `products.p3.engine:analyze` entrypoint, a small loopback-only HTTP reference host, and a React suite module. The host is limited to P3 request dispatch, the existing official SDK adapter, evidence/result shaping, and local assets; it is not a reusable general API framework. Current tests exercise real loopback SDK workflow requests, typed maps, request limits, same-origin checks, cancellation, refusal, provenance and export. No custom MCP transport is used.

P3 keeps the standard-library `unittest` scientific suite and its own locked Vitest/Testing Library/happy-dom and TypeScript toolchain for the host and panel. npm dependencies are installed from cache for builds and excluded from the transfer archive; only built static assets and lock metadata are packaged. Golden's local runner and rules are v0.1.0-dev pilot tooling, not complete qualification; its supported local checks are replayed and unsupported MCP/API/science/browser controls remain explicit.

Golden's offline packager is a source-only package tool tied to its own clean-worktree and package identity. P3 retains its existing product-specific deterministic archive builder, adopts per-file hash, fresh-extraction, and offline-install checks, and includes its hash-locked local SDK wheelhouse. The archive-hash-dependent `GATE_REPORT.json` remains adjacent to the ZIP and is excluded from both archive contents and the embedded bootstrap manifest; resumable execution ledgers under `progress/` are also excluded. This avoids circular/self-referential release evidence while preserving product, test and critical-case evidence in the candidate. P3 does not use Golden as a binary staging service or infer approval from a successful local install.

## MCP and semantic authority

**Selected:** Official Model Context Protocol Python SDK 2.3.0 as the protocol/transport implementation, with P3's existing logical `ReadOnlyMCPAdapter` preserving reviewed operation bindings, bounded read limits, authorization checks, provenance and refusal behavior. The local candidate is pinned to upstream commit `2118f14f8a19bc158d8a1cf90af58d85d187f849`; its complete macOS arm64 CPython 3.11 wheelhouse, requirements hash lock, license inventory and CycloneDX SBOM are in `vendor/mcp-sdk-2.3.0/macos-arm64-cp311/`. It was copied from a local sibling-product vendor directory and installed with pip `--no-index --require-hashes` in an isolated environment.

The SDK is a candidate, not company-cleared. Golden's candidate manifest records no company OSS approval, no independent vulnerability review, no native Windows/Linux install, and no company OpenCode handshake. The synthetic peer exercises approved logical bindings and pinned source snapshots through bounded reads, normalized scientific inputs, C01–C05 and correlated evidence. The exact current full-suite count is in `release/MCP_SDK_OFFLINE_QUALIFICATION.json`. No credentials, real server names, semantic mappings, approvals or internal endpoints were supplied. Fab Insight MCP remains the sole real semantic authority.

## Scientific methods and dependencies

P3 keeps its existing deterministic, dependency-free scientific core and independent arithmetic/metamorphic oracles. Existing tests cover coordinate/orientation refusals, non-interpolation, independence and holdout requirements, overlap/aliasing, missing center sites, source provenance, and synthetic false-alert behavior. The installed NiceGUI Base spatial helpers were inspected as a reuse candidate. They provide radial/sector summaries, center-edge decomposition, deltas, and exploratory contour/defect helpers; they do not provide P3's population compatibility, same-wafer/time lineage, matched-lot max-T test, historical exclusion rules, or block-adjusted outcome design. A matched synthetic boundary fixture with physical radius 100 and sampled radius only 60 gives the independent oracle/P3 `INCONCLUSIVE` with zero measured edge sites, while NiceGUI Base's maximum-observed-radius normalization reports two outer sites and a 7-unit center-edge difference. The mismatch is recorded in `release/REUSE_COMPARISON_EVIDENCE.json`. These methods were not substituted; an equivalence claim would require passing the existing independent refusal/oracle suite, and the package has no distribution license metadata in the staged copy. Golden's capability registry identifies Polars only as a candidate for large local-data analytics; P3's measured inputs and deterministic index do not show a need for that dependency. No candidate library has demonstrated a qualified improvement across P3's accepted scientific methods, offline targets, and license checks, so no spatial/statistical runtime package was added. This is not a claim that all P3 scientific methods have source-derived or held-out qualification.
